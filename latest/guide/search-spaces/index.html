    Search spaces¶

    Parameters¶

    Class Values Example
    RangeParameter A number between minimum and maximum; integer=True restricts it to whole numbers, and log=True searches it on a log scale RangeParameter("rate", 0, 1)
    ChoiceParameter One of a list of choices, or a list of choose_n distinct choices ChoiceParameter("kernel", ["linear", "rbf"])
    FixedParameter A single value that never changes FixedParameter("mode", "fast")

    Use log=True for settings that span orders of magnitude, such as learning rates, regularization strengths or tree counts. Values are then spread evenly in their logarithm, so 0.001 to 0.01 is searched as thoroughly as 100 to 1000, and every optimizer searches the range that way. A log range needs a positive minimum, and works with integer=True:

    RangeParameter("learning_rate", 1e-5, 1e-1, log=True)
RangeParameter("n_estimators", 10, 1000, integer=True, log=True)

    Every parameter the objective function requires must be in the search space. The optimizer checks this before it starts.

    Constraints¶

    Limits across parameters are written with the parameters themselves and passed to SearchSpace. Every optimizer then only asks for points that satisfy every constraint, so the objective is never evaluated outside them:

    from hone import RangeParameter, SearchSpace

width = RangeParameter("width", 1, 10)
height = RangeParameter("height", 1, 10)
search_space = SearchSpace([width, height], constraints=[width * height <= 40, width >= 2 * height])

    Range parameters and numbers combine with +, -, *, /, ** and abs(), and <= or >= makes the result a constraint; < and > mean the same. A point where a constraint can't be computed, such as one that divides by zero, counts as breaking it. There are no equality constraints: an equality leaves nothing to sample, so remove a variable instead and compute it inside the objective. Write a range as two constraints, since Python reads 0 <= width - height <= 5 as two comparisons joined by and, and hone raises an error rather than keep one half.

    For anything an expression can't say, such as a square root or a choice parameter, use a function, which takes parameters by name and is satisfied when it returns zero or less:

    from hone import Constraint

def stress(width, height, material):
    return bending_stress(width, height) - ALLOWED[material]

search_space = SearchSpace([width, height, material], constraints=[Constraint.function(stress)])

    Constraints should be quick to check: hone checks them for every candidate it considers, which can be many times the number of evaluations. Expression constraints are saved with a result; a function constraint saves only its name, so after Result.load pass the function again with rebuild_optimizer(functions={"stress": stress}).

    Starting points must satisfy the constraints. If the constraints leave nothing to search, or a region too small to find in 100,000 random draws, the optimizer raises InfeasibleSearchSpace when it's created, before any evaluation. Each optimizer keeps to constraints in its own way: random search and Bayesian optimization only consider points that satisfy them, CMA-ES draws a candidate again while it breaks one, and the genetic optimizer moves such a child back toward its fitter parent until it is feasible, which tends to land it near the boundary, where constrained optima usually are. On the benchmark's constrained problems the choice between optimizers follows the same pattern as without constraints; see benchmarks/README.md. examples/pressure_vessel.py designs a pressure vessel of least cost under three constraints and finds the best published design. examples/maintenance_schedule.py chooses a maintenance schedule for a production line, scored by a noisy simulation of a year, with a constraint on technician hours and a function constraint that depends on the chosen shift; it halves the expected yearly cost of a sensible schedule chosen by hand.

    Constraints on outputs¶

    Some limits can't be checked until a design has been evaluated: the peak stress a simulation reports, a temperature, a latency. Write them the same way, with Output standing for the reported value, and pass them in the same list:

    from hone import BayesianOptimizer, Output, SearchSpace

stress = Output("stress")
search_space = SearchSpace(
    [width, height],
    constraints=[
        width * height <= 40,  # on the parameters: checked before evaluating
        stress <= 250,  # on an output: judged once the evaluation reports it
        stress <= 50 * width,  # outputs and parameters can mix
    ],
)

def simulate(width, height):
    ...
    return {"objective": mass, "stress": peak_stress}

result = BayesianOptimizer(search_space).optimize(simulate)
result.feasible  # whether best_params satisfies every limit on the outputs
result.best_outputs  # {"stress": ...} at best_params

    With constraints on outputs, the objective returns a dict: its value under "objective", and a number for each output the constraints use. With several objectives, the outputs go in the same dict as the objectives, and a name can be both, so Output("cost") <= 20 limits an objective. A dict with missing or extra keys, or a value that isn't a number, raises TypeError, and NaN or infinity anywhere in it marks the evaluation as failed. tell(trial, {...}) takes the same dict. Outputs work everywhere parameters do in an expression, including test >> constraint, as in material["steel"] >> (stress <= 400). They can't appear in a test, on the left of >>, because which parameters the objective is passed can't depend on what it returns. A function constraint takes outputs by name too: Constraint.function(f, outputs=["stress"]).

    A design that breaks a limit on an output has already been evaluated, so it can't be skipped; instead it is ranked by Deb's feasibility rule, with no penalty weight to tune. A design that satisfies every limit beats one that doesn't, those that do rank by their value, and those that don't rank by their total violation. Each violation is a share of its limit when the limit is a number, as in stress <= 250, so 10% over a stress limit counts the same as 10% over a deflection limit. A limit that varies with the design, such as stress <= 50 * width, a limit of zero and a function constraint count in their own units, so when several limits share a problem, write each with its number on one side, and have a function return a share, such as stress / LIMIT - 1. best_params is the best design that satisfies every limit. If none did, it is the one that came closest, and feasible is False. Each generation's statistics count the designs that broke a limit in infeasible and leave them out of the fitness figures. A threshold is reached only by a design that satisfies every limit. On a front, only such designs appear, and each point carries its outputs.

    Bayesian optimization makes the most of these limits. It models each limit with a Gaussian process, learning from the designs that broke one, and multiplies its expected improvement by the probability that a candidate satisfies them all, treating the limits as independent, so two limits that say nearly the same thing make it more cautious there than it need be; until it finds a design that does, it looks for one. The other optimizers only learn which designs ranked lower. On the benchmark's engineering problems with their limits on outputs, Bayesian optimization comes close to its results when the same limits are known before evaluating, while the genetic optimizer and CMA-ES lose more; see benchmarks/README.md. Constraints on outputs aren't supported with noise=True yet, since a noisy design can pass a limit by luck. sensitivity() accepts them and measures only the objective. examples/welded_beam.py designs a welded beam whose stresses, buckling load and deflection come from an analysis of each design, and gets within about 1% of the best published design in 150 evaluations.

    Conditional parameters¶

    Some settings only exist when another takes certain values: a kernel's settings only for the model that has kernels, a third layer's size only with three layers or more. Write each condition as test >> parameters, read "then", and pass them to SearchSpace:

    from hone import ChoiceParameter, RangeParameter, SearchSpace

model = ChoiceParameter("model", ["svm", "forest"])
kernel = ChoiceParameter("kernel", ["linear", "rbf"])
C = RangeParameter("C", 1e-3, 1e3, log=True)
gamma = RangeParameter("gamma", 1e-5, 1, log=True)
trees = RangeParameter("trees", 10, 500, integer=True)

search_space = SearchSpace(
    [model, kernel, C, gamma, trees],
    conditions=[
        model["svm"] >> [kernel, C],
        kernel["rbf"] >> gamma,  # only with an svm too, since kernel is
        model["forest"] >> trees,
    ],
)

def train(model, kernel=None, C=None, gamma=None, trees=None):
    ...

    The left of >> is a test: a choice parameter indexed by the values that switch the parameters on, such as model["svm"] or optimizer["sgd", "nesterov"], or a comparison of range parameters in brackets, such as (layers >= 3) >> units_3. The brackets are needed, since Python reads layers >= 3 >> units_3 as layers >= (3 >> units_3); hone raises an error saying so. The right is a parameter or a list of them, and each parameter can have one condition. Conditions nest: a parameter whose test uses a parameter that is switched off is off too.

    A parameter that is switched off isn't part of the point. The objective isn't passed it, so give it a default, which hone checks before the run starts; results, progress and best_params leave it out; and a starting point must leave it out too. Two points that differ only in a parameter switched off are the same point, so they are averaged together with noise=True and the genetic optimizer doesn't count one as new.

    A constraint applies only while every parameter it uses is switched on, and test >> constraint makes a constraint apply only while the test holds:

    depth = RangeParameter("depth", 2, 20, integer=True)
search_space = SearchSpace(
    [model, trees, depth],
    constraints=[model["forest"] >> (trees * depth <= 2000)],
    conditions=[model["forest"] >> [trees, depth]],
)

    Every optimizer supports conditions; CMA-ES only conditions on range parameters, since it doesn't search choices. Bayesian optimization gains the most: a parameter switched off looks the same to its model whatever value it holds, so values that don't matter add no noise. On the benchmark's conditional problems its error is ×0.0004 that of searching every parameter all the time, at 10 evaluations per dimension. With conditions the genetic optimizer breeds each branch within its own niche by default (niche_share of 0.5, below), so a wide, easy branch doesn't crowd out a narrow, better one; see benchmarks/README.md. examples/choose_a_model.py chooses a classifier, among an SVM with three kernels, a random forest and logistic regression, together with its settings.

    Starting points¶

    If you already have a good design, or the best parameters from an earlier run, pass it as a starting point so the search doesn't begin from scratch:

    optimizer = CMAES(search_space, CMAESConfig(max_evaluations=500), initial_points={"thickness": 2.5, "width": 40})

# or continue from an earlier result
optimizer = GeneticOptimizer(search_space, config, initial_points=[earlier.best_params])

    initial_points takes one dict of parameter values or a list of them; fixed parameters may be left out, and every value is checked against the search space. The points are evaluated first and count toward the budget. The genetic optimizer and random search put them in their first generation, filling the rest with random candidates. CMA-ES evaluates them, then centres its search on the best one; lower initial_step to keep the search close to it.
